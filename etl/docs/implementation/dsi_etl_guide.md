# DSI ETL Guide — Source System to Archive Table

This guide covers the DSI layer: getting data out of a source system and into a
persistent archive table that the rest of the platform can build on.

Two chapters, matching the two situations you can be in:

- **[Chapter 1: Onboarding a new source system](#chapter-1-onboarding-a-new-source-system)**
  — one-time work per source: access, resource, DDL home, config modules, job, DQA.
- **[Chapter 2: Adding a new table](#chapter-2-adding-a-new-table)** — the same
  steps whether the source is brand new or has been running for years.

If the source system already exists, skip straight to chapter 2.

## The DSI contract

Everything in this guide follows from five rules. Break one and the failure shows
up far downstream, usually as wrong data rather than an error.

1. **`ext.*` is volatile, `arc.*` is permanent.** Each extract run drops and
   recreates its `ext` table. The archive MERGE is the only thing that persists.
2. **Downstream reads `arc.*`, never `ext.*`.** No staging, FHIR or DQA asset may
   reference `ext`. `ext` exists only as the MERGE source.
3. **No business logic in DSI.** No CleanCodes, no renaming, no derived columns,
   no filtering rows for business reasons. `arc.*` is a 1:1 reflection of the
   source table plus DWH audit columns. Business logic starts in `pre_stg` or `stg`
   (DWH track) or in the FHIR transform.
4. **One archive table per source table.** Joins to enrich or denormalize belong
   downstream, not here. (The one exception —`select_from_expr` for pulling a
   delete flag from a companion table — is described under [Delete detection](#delete-detection).)
5. **The archive is the replay point.** Because `arc.*` holds full history, any
   downstream layer can be rebuilt without touching the source system. This is
   the whole reason the layer exists — protect it.

### Naming

| Thing | Pattern | Example |
|---|---|---|
| Landing table | `ext.{source}_{source_table}` | `ext.ils_vare`, `ext.ifdb_encounter` |
| Archive table | `arc.{source}_{source_table}` | `arc.ils_vare`, `arc.sydax_afdeling` |
| Extract asset | `ext_{target_table}` | `ext_ils_vare` (generated by the factory) |
| Archive asset | `arc_{target_table}` | `arc_ils_vare` |
| Asset group | `{source}_archive` | `ils_archive`, `sydax_archive` |
| DDL file | `infrastructure/ddl/tables/{domain}/00_archive.sql` | |

The source name comes **first** in the table name. Two deviations exist and must
not be copied: the hand-written IFDB archive assets in `DSI/oracle/ifdb_archive.py`
are named `arc_{table}_ifdb`, and the legacy partitioned ILS extract in
`DSI/mssql/ils.py` writes source-suffixed `ext.{table}_ils` tables. New tables use
the table above.

**Source identifiers stay as the source spelled them.** `ext` and `arc` tables
and columns are a 1:1 mirror of the source (plus DWH audit columns and any
keys *we* add). Do not transliterate or rename the source's own identifiers
to match `ae`/`oe`/`aa` — that rule starts downstream of the archive. Columns
we add (`dw_*`, resolved `*_uuid` / `*_noegle`) follow
[navngivningsstandard.md](navngivningsstandard.md#extract-og-arkiv-extarc).
Source-copied columns keep the source's casing (`DIAGNOSE` vs `Diagnose`).

### Standard columns on `arc.*`

Every archive table carries the source columns 1:1, plus:

```sql
[dw_timestamp_insert] DATETIME2 NOT NULL,   -- when the row first reached the archive
[dw_timestamp_update] DATETIME2 NOT NULL,   -- when it was last MERGEd
[dw_is_deleted]       BIT NOT NULL DEFAULT 0  -- only when delete detection is on
```

`ext.*` tables get no audit columns beyond what the extractor adds (`SourceSystem`).

## Chapter 1: Onboarding a new source system

Do this once per source system. The result is an empty but fully wired source:
a connection, a place for its DDL, its config modules, a job, and a DQA slot. You
then add tables to it with chapter 2.

### 1. Establish access, and document it

Before writing code, get from whoever owns the source system: host, port, database,
a **read-only** service account, and confirmation that the network path from the
Dagster runtime exists. Note whether the source is on-prem MSSQL, Azure Synapse,
Oracle, or a file drop — this decides the connection library in step 3.

Add the settings to [`.env.template`](../../../.env.template) with placeholder values,
grouped under a comment header like the existing sources:

```bash
# ---------------------------------------------------------------------------
# MySource database
# ---------------------------------------------------------------------------
MYSOURCE_PROD_MSSQL_SERVER=mssql
MYSOURCE_PROD_MSSQL_PORT=1433
MYSOURCE_PROD_MSSQL_DATABASE=mysource
MYSOURCE_PROD_MSSQL_USERNAME=sa
MYSOURCE_PROD_MSSQL_PASSWORD=tempPassword1!
MYSOURCE_PROD_MSSQL_SCHEMA=dbo
```

`.env.template` is the list of variables the resource requires; the real values come
from the deployment's environment. **Never commit real credentials** — the gitleaks
pre-commit hook scans the staged diff and CI scans the history.

### 2. Document the source schema

Create `docs/source_systems/{source}/` with at least a schema overview: tables you
expect to use, their grain, primary keys, and whatever the source owner told you
about delta columns and deletes. See
[`source_systems/ifdb/ifdb_schema.md`](../source_systems/ifdb/ifdb_schema.md) and
[`source_systems/bom_ifdb/bom_ifdb.md`](../source_systems/bom_ifdb/bom_ifdb.md)
for the level of detail that has proven useful.

This is not busywork. Every question chapter 2 asks you about a table ("what is
the grain?", "is there a modification timestamp?") is answered here once instead of
re-investigated per table.

### 3. Add a Dagster resource

Resources live in [`core/resources.py`](../../core/resources.py). Copy the pattern
that matches your connection library:

```python
class MySourceMSSQLResource(dg.ConfigurableResource):
    """A Dagster resource for connecting to the MySource Microsoft SQL Server database."""

    host: str = dg.EnvVar("MYSOURCE_PROD_MSSQL_SERVER").get_value()
    port: int = int(dg.EnvVar("MYSOURCE_PROD_MSSQL_PORT").get_value())
    database: str = dg.EnvVar("MYSOURCE_PROD_MSSQL_DATABASE").get_value()
    user: str = dg.EnvVar("MYSOURCE_PROD_MSSQL_USERNAME").get_value()
    password: str = dg.EnvVar("MYSOURCE_PROD_MSSQL_PASSWORD")

    @contextmanager
    def get_connection(self):
        """A context manager that yields a pymssql connection and closes it when exiting."""
        password = self.password
        if hasattr(password, "get_value"):
            password = password.get_value()
        conn = pymssql.connect(
            server=self.host,
            port=self.port,
            user=self.user,
            password=password,
            database=self.database,
        )
        try:
            yield conn
        finally:
            conn.close()
```

| Source kind | Follow | Library |
|---|---|---|
| On-prem MSSQL | `ILSMSSQLResource`, `SydaxMSSQLResource` | `pymssql` |
| Azure Synapse / cloud MSSQL | `KmdUddataMSSQLResource` | `mssql-python` via `build_mssql_conn_str()` + `_connect_mssql_python()` |
| Oracle | `IFDBOracleResource` | `oracledb` |
| CSV / file drop | `DSI/connectors/csv_files/` | — |

The password stays a `dg.EnvVar` (resolved at run time, redacted in logs); the other
fields may resolve at import time. Synapse has a cold-start latency — pair it with
a retry policy on the assets, as KMD does.

### 4. Register the resource

In [`definitions.py`](../../definitions.py), import the class and add it to the
`resources` dict:

```python
resources = {
    **mssql_resources,
    "mysupply_mssql": MySupplyMSSQLResource(),
    "ils_mssql": ILSMSSQLResource(),
    "mysource_mssql": MySourceMSSQLResource(),   # <- new
    "ifdb_oracle": IFDBOracleResource(),
    **fhir_resources,
}
```

The dict key is what you pass as `source_resource_key` to the extract factory, and
what assets receive by parameter name.

### 5. Decide where the archive DDL lives

`arc.*` tables need hand-written, checked-in DDL. (`ext.*` tables do not — the
extractors drop and recreate them from the source schema on every run.)

- **Source belongs to an existing domain** (e.g. another ERP system): add its
  `CREATE TABLE` blocks to that domain's archive file, e.g.
  `infrastructure/ddl/tables/erp/00_archive.sql`. Nothing else to do.
- **Source is its own domain**: create `infrastructure/ddl/tables/{source}/00_archive.sql`
  and add a `staging_infra_{source}` asset that executes the folder. Follow the
  four-file registration chain:

  1. `infrastructure/assets/staging_infrastructure.py` — add the asset
  2. `infrastructure/assets/__init__.py` — import and export it
  3. `infrastructure/__init__.py` — add to `all_staging_assets` and `__all__`
  4. reference it from your extract assets via `deps=["staging_infra_{source}"]`

  A DSI-only source needs **no** `dso_infra_*` counterpart — `arc.*` lives on the
  staging database and is never synced to DSO.

```python
@dg.asset(
    name="staging_infra_mysource",
    group_name="staging_infrastructure",
    compute_kind="mssql",
    deps=["staging_infra_schemas", "staging_infra_functions"],
    description="Create arc.* tables for the MySource archive.",
)
def staging_infra_mysource(
    context: dg.AssetExecutionContext, mssql_target_staging: MSSQLResource
) -> dg.MaterializeResult:
    results = execute_sql_files_from_directory(mssql_target_staging, "tables/mysource", context)
    return dg.MaterializeResult(metadata={"files_executed": len(results)})
```

### 6. Create the config modules

Two modules, one per layer. They start empty except for the factory call — chapter 2
fills them in.

```
DSI/mssql/extract/mysource_extract_configs.py    # DfmExtractConfig list + factory call
DSI/mssql/archive/mysource_archive_configs.py    # ArchiveMergeConfig list + asset factory
```

For an Oracle source, the equivalents are `DSI/oracle/{source}_extract.py` and
`DSI/oracle/{source}_archive.py`.

Extract side — the factory generates one asset per config:

```python
"""DFM extract configs and factory-generated assets for MySource."""

from core.resources import MySourceMSSQLResource
from DSI.connectors.extract_config import DfmExtractConfig
from DSI.connectors.factory import create_dfm_extraction_assets

MYSOURCE_EXTRACT_CONFIGS: list[DfmExtractConfig] = [
    # chapter 2 adds configs here
]

mysource_extract_assets = create_dfm_extraction_assets(
    configs=MYSOURCE_EXTRACT_CONFIGS,
    source_resource_key="mysource_mssql",
    source_resource_type=MySourceMSSQLResource,
    source_system="MySource",
    group_name="mysource_archive",
    domain_tag="erp",
    dialect="mssql",
    deps=["staging_infra_mysource"],
)
```

Archive side — one asset per `ArchiveMergeConfig`, generated the same way. Copy
`_make_arc_asset()` from
[`DSI/mssql/archive/sydax_archive_configs.py`](../../DSI/mssql/archive/sydax_archive_configs.py);
it derives the asset name, the `ext_*` dependency and the entity tag from the config,
so adding a table is a config entry and nothing else:

```python
def _make_arc_asset(cfg: ArchiveMergeConfig):
    name = f"arc_{cfg.target_table}"
    ext_key = f"ext_{cfg.source_table}"
    entity = cfg.target_table.removeprefix("mysource_")

    @dg.asset(
        name=name,
        group_name="mysource_archive",
        compute_kind="mssql",
        deps=[dg.AssetKey([ext_key])],
        tags={"domain": "erp", "layer": "archive", "source": "mysource", "entity": entity},
        description=f"UPSERT ext.{cfg.source_table} → arc.{cfg.target_table}.",
    )
    def _asset(
        context: dg.AssetExecutionContext,
        mssql_target_staging: MSSQLResource,
        config: RunModeConfig,
    ) -> dg.MaterializeResult:
        result = execute_archive_merge(context, mssql_target_staging, cfg, config)
        context.log.info(
            f"MERGEd {result.row_count} rows into arc.{cfg.target_table}; "
            f"mode={config.mode}, checkpoint → {result.new_checkpoint}"
        )
        return dg.MaterializeResult(
            metadata=build_archive_metadata(
                result,
                config,
                source_table=f"ext.{cfg.source_table}",
                target_table=f"arc.{cfg.target_table}",
            )
        )

    return _asset


mysource_archive_assets = [_make_arc_asset(cfg) for cfg in MYSOURCE_ARCHIVE_CONFIGS]
```

Both extract and archive assets belong to the **same group** (`{source}_archive`), so
one job selection covers the whole source.

### 7. Wire the exports

Four `__init__.py` hops carry the assets to `definitions.py`:

```python
# DSI/mssql/extract/__init__.py
from .mysource_extract_configs import MYSOURCE_EXTRACT_CONFIGS, mysource_extract_assets

all_factory_extract_assets = (
    ils_unspsc_extract_assets
    + ...
    + mysource_extract_assets
)

# DSI/mssql/archive/__init__.py
from .mysource_archive_configs import mysource_archive_assets

all_archive_assets = [..., *mysource_archive_assets]
```

`DSI/mssql/__init__.py` already re-exports `all_factory_extract_assets` and
`all_archive_assets`, and `definitions.py` already spreads both into `all_assets` —
so if you appended to those two lists there is nothing more to register.

### 8. Add a job

```python
# jobs/mysource_jobs.py
import dagster as dg

mysource_archive_job = dg.define_asset_job(
    name="mysource_archive_job",
    selection=dg.AssetSelection.groups("mysource_archive"),
    description="DFM extract + archive of the MySource tables.",
    tags={"domain": "erp", "layer": "archive", "source": "mysource"},
)
```

Register it in `jobs/__init__.py` (import + add to the exported job list). Then decide
how it runs in production:

- **Part of the ERP daily chain** — add `"mysource_archive"` to the group list in
  [`jobs/erp_daily_dfm_jobs.py`](../../jobs/erp_daily_dfm_jobs.py). This is the
  default for ERP-ish sources; the standalone job stays available for manual runs.
- **Its own schedule** — add a `dg.ScheduleDefinition` under `schedules/` and register
  it in `schedules/__init__.py`.

### 9. Add a DQA source slot

Archive tables are checked by the `archive_reconciliation` check: every current
source key must exist in `arc.*`, and archive keys that vanished from the source must
be soft-deleted rather than left stale.

Create `dqa/config/arc_mysource_subjects.py` modelled on
[`dqa/config/arc_subjects.py`](../../dqa/config/arc_subjects.py), and add its subject
list to `ALL_SUBJECTS` in `dqa/config/__init__.py`. Setting `source="mysource"` gives
the source its own anchor assets, its own `dqa_arc_mysource_weekly_job` and its own
schedule automatically.

Take `key_columns` from the `ArchiveMergeConfig.merge_keys` object rather than
retyping them — that is what keeps DQA from drifting away from the archive's actual
grain when a merge key changes.

### 10. Add test fixtures

In [`tests/conftest.py`](../../tests/conftest.py), add a mocked and a real-resource
fixture for the new resource, following `mock_ils_mssql_resource` /
`real_ils_mssql_resource`. Downstream integration tests need them to inject the source
connection.

### New-source checklist

- [ ] Read-only credentials obtained; connectivity from the Dagster runtime verified
- [ ] `.env.template` updated with placeholders for the variables the resource requires
- [ ] `docs/source_systems/{source}/` created
- [ ] Resource class added to `core/resources.py`
- [ ] Resource registered in `definitions.py`
- [ ] Archive DDL home decided (existing domain folder, or new folder + `staging_infra_{source}` through the 4-file chain)
- [ ] `{source}_extract_configs.py` and `{source}_archive_configs.py` created with factory calls
- [ ] Assets exported through `extract/__init__.py` and `archive/__init__.py`
- [ ] `jobs/{source}_jobs.py` added and registered; schedule or daily-job membership decided
- [ ] `dqa/config/arc_{source}_subjects.py` created and added to `ALL_SUBJECTS`
- [ ] Test fixtures added to `tests/conftest.py`
- [ ] The code location loads and the assets appear in the Dagster UI after the push

## Chapter 2: Adding a new table

This is identical whether the source system is new or long-established. Five files
change; the rest is investigation.

### 1. Investigate the source table

Do not skip this. Every wrong answer here becomes a silent data bug that surfaces
weeks later. Answer all six before writing config:

| Question | Why it matters | How to check |
|---|---|---|
| **What is the grain?** One row per what? | Decides `merge_keys` | `SELECT COUNT(*), COUNT(DISTINCT <candidate>) FROM <table>` — must match |
| **Is there a stable primary key?** | Without one, upsert is impossible | Source DDL; confirm it is never reused after delete |
| **Is there a modification timestamp?** | Decides delta vs full load | Look for `modified`, `sysdato`, `*_MODIFICATION_DATETIME`, audit ints |
| **Does that timestamp update on *every* change?** | A column that only tracks inserts silently loses updates | Ask the source owner; spot-check known-edited rows |
| **How are deletes represented?** | Decides `detect_deletes` / `source_delete_column` | Soft-delete flag, a deletion-log table, or hard delete |
| **How large is it?** | Decides full load vs delta, and bulk-insert on first load | `SELECT COUNT(*)`, and daily change volume |

Record the answers in `docs/source_systems/{source}/`.

### 2. Make the four load decisions

**Full load or delta?**

| Choose | When |
|---|---|
| `is_full_load=True` | Small reference tables (say, under ~100k rows), or no trustworthy modification timestamp. Simpler and self-healing: every run re-reads everything. |
| Delta | Large or high-churn tables with a reliable modification timestamp. |

A full-load extract is not a full-load *archive* — the archive still MERGEs, so
history is preserved either way.

**Which delta column?** Use `delta_column` for a plain column, `delta_expression`
for something computed:

```python
delta_column="sysdato"
delta_expression="GREATEST([dw_audit_insert], [dw_audit_update])"
```

Set `checkpoint_type="datetime"` (default) or `"int"` to match. Add
`lookback_days=N` when the source writes rows with a slightly stale timestamp —
it re-reads a safety window on every run, and the MERGE makes that harmless.

**What is the merge key?** The business key that identifies a row over its lifetime —
`("prrowid",)` for ILS, `("OBJECT_ID", "PERIOD_START")` for IFDB Location. It must be
unique in the source and stable across updates. It is a `tuple`, and a one-element
tuple **needs the trailing comma** (the dataclass raises a clear error if you pass a
bare string).

**Do deletes need detecting?** See [Delete detection](#delete-detection) below.

### 3. Write the archive DDL

Add a `CREATE TABLE` block to the source's archive DDL file. Source columns 1:1 with
source types, then the audit columns:

```sql
-- ============================================================================
-- Archive: orders from MySource
-- 1:1 reflection of MySource.dbo.orders (12 columns)
-- Used by arc_mysource_orders archive merge asset
-- ============================================================================

IF NOT EXISTS (
    SELECT 1 FROM INFORMATION_SCHEMA.TABLES
    WHERE TABLE_SCHEMA = 'arc' AND TABLE_NAME = 'mysource_orders'
)
BEGIN
    CREATE TABLE [arc].[mysource_orders] (
        [order_id]      VARCHAR(36)    NOT NULL,
        [customer_id]   VARCHAR(24)    NULL,
        [amount]        DECIMAL(18,3)  NULL,
        [modified]      DATETIME       NULL,

        -- DWH audit columns
        [dw_timestamp_insert] DATETIME2 NOT NULL,
        [dw_timestamp_update] DATETIME2 NOT NULL
    );
END
GO
```

Rules that bite if ignored:

- Guard every `CREATE TABLE` with `IF NOT EXISTS` and separate blocks with `GO`.
- Add `[dw_is_deleted] BIT NOT NULL DEFAULT 0` when delete detection is on.
- **Changing an existing archive table needs the change in two places** — the base
  DDL here *and* a migration under `infrastructure/ddl/migrations/`. The base DDL is
  all a fresh database gets; the migration is all an existing one gets. See the
  migration patterns in [sql_etl_guide.md](sql_etl_guide.md#sql-migration-patterns).
- Do not add indexes beyond what the MERGE needs. The archive is written far more
  often than it is read directly.

### 4. Add the extract config

Append a `DfmExtractConfig` to the source's config list:

```python
DfmExtractConfig(
    source_schema="dbo",
    source_table="orders",
    target_table="mysource_orders",
    delta_column="modified",
    checkpoint_type="datetime",
    checkpoint_from=("arc", "mysource_orders"),
    description="MySource orders (delta via modified).",
),
```

`checkpoint_from` points at the **archive** table, not the ext table — the checkpoint
must reflect what was durably archived, not what was merely extracted. A run that
extracts successfully but fails to merge must re-extract next time. For a full-load
table with no checkpoint, set `checkpoint_from=None`.

**Oracle sources need two more fields.** `columns` is mandatory, and `column_types`
should be supplied so the `ext` table gets properly sized columns — without it every
column becomes `NVARCHAR(MAX)`, which SQL Server cannot index, and the archive MERGE
degrades badly. Add `index_keys` for the post-load clustered index:

```python
DfmExtractConfig(
    source_schema="IFDB",
    source_table="ORDERS",
    target_table="ifdb_orders",
    delta_column="IFDB_MODIFICATION_DATETIME",
    checkpoint_type="datetime",
    checkpoint_from=("arc", "ifdb_orders"),
    columns=ORDERS_COLUMNS,
    column_types=ORDERS_COLUMN_TYPES,
    index_keys=("OBJECT_ID",),
    description="IFDB Orders (delta).",
),
```

Full field reference: [dfm_extract_factory_guide.md](dfm_extract_factory_guide.md#dfmextractconfig-fields).

### 5. Add the archive config

Append an `ArchiveMergeConfig` to the source's archive list:

```python
ORDERS_ARCHIVE_CONFIG = ArchiveMergeConfig(
    source_schema="ext",
    source_table="mysource_orders",
    target_schema="arc",
    target_table="mysource_orders",
    merge_keys=("order_id",),
    non_key_columns=("customer_id", "amount", "modified"),
    checkpoint_query=(
        "SELECT CONVERT(NVARCHAR(50), MAX([modified]), 121) FROM [arc].[mysource_orders]"
    ),
    strategy="upsert",
    update_only_on_change=True,
)
```

`merge_keys` + `non_key_columns` together must list **every** column the archive
carries — anything omitted is silently never written. List the non-key columns in
source order and copy them from the source DDL rather than re-deriving them.

If the source module uses an asset factory (step 6 of chapter 1), the asset appears
as soon as the config is in the list. Otherwise add the `@dg.asset` by hand,
mirroring a neighbour.

#### The checkpoint query

`checkpoint_query` computes the new checkpoint from the **archive** after the merge.

**Always wrap datetimes in `CONVERT(NVARCHAR(50), ..., 121)`.** A plain `CAST` of a
`datetime` yields style 0 (`Jun 23 2026 12:00AM`), which
`utils/sql_safety.validate_checkpoint_value` rejects — the run fails at the very end,
after the expensive part. Omit `checkpoint_query` entirely for full-load tables that
carry no checkpoint.

#### Delete detection

The archive is the platform's memory, so a row disappearing from the source must be
handled deliberately.

| Situation | Config |
|---|---|
| Source hard-deletes rows, and the extract is a **full load** | `detect_deletes=True` + `upstream_is_full_load=True` |
| Source has its own delete flag column | `source_delete_column="DELETED"` |
| Source has a separate deletion-log table (Oracle only) | `select_from_expr=` with a `LEFT JOIN` producing `dw_is_deleted` |
| Rows are never deleted | leave the defaults |

There is a safety gate you should understand rather than fight: `detect_deletes`
generates `WHEN NOT MATCHED BY SOURCE THEN ... dw_is_deleted = 1`, which is only
correct if `ext` holds the *complete* current row set. On a delta run it does not, so
the merge engine disables delete detection at run time unless the run is `full_load`
mode or `upstream_is_full_load=True`, and logs a warning. If you see that warning on
a table you expected to soft-delete, the fix is the extract config, not the flag.

Full flag reference: [archive_merge_options.md](archive_merge_options.md).

### 6. Register and validate

- Config in the list → asset generated → already exported if the source was onboarded
  per chapter 1. Verify that the asset appears in your branch's code location after
  the push.
- If you added the table to a **new** group, add that group to a job selection.
- Add the table to the source's DQA subject list (`dqa/config/arc_{source}_subjects.py`).
  Take `key_columns` from the `ArchiveMergeConfig` object, not a retyped copy.
- Add lineage YAML only when the table feeds a DSO-synced `dim`/`fct`/`fhir` target —
  archives themselves are not lineage-documented. See
  [data_lineage_guide.md](data_lineage_guide.md).

### 7. Run and verify

Push the branch, then materialize in the Dagster UI on Dev — in your own code
location, where asset names carry the branch postfix. In order:
`staging_infra_{source}` (creates the arc table) → `ext_{source}_{table}` →
`arc_{source}_{table}`, or materialize the whole `{source}_archive` group at once.

Then check five things:

1. **Row counts.** `arc` count matches the source count for a full load; for a delta,
   the first run should have loaded everything (checkpoint was empty).
2. **The checkpoint advanced.**
   ```sql
   SELECT * FROM [meta].[DFMState] WHERE [table_name] = 'mysource_orders';
   SELECT TOP 20 * FROM [meta].[DFMRunLog] ORDER BY [start_time] DESC;
   ```
   The `DFMState` row is created automatically on the first run — there is nothing
   to seed by hand.
3. **The second run is a no-op.** Materialize again immediately: the extract should
   pull ~0 rows and the archive should report 0 inserted, 0 updated. If the second
   run re-merges everything, the delta column or checkpoint query is wrong.
4. **Grain holds.** `SELECT COUNT(*), COUNT(DISTINCT <merge_keys>) FROM arc.mysource_orders`
   — the two numbers must be equal. If they diverge, `merge_keys` does not match the
   real grain, and every downstream join will double-count.
5. **A replay works.** Run one ad-hoc period or ids run per
   [dfm_operations_guide.md](dfm_operations_guide.md) and confirm the production
   checkpoint did **not** move. This is the guarantee that lets operations fix data
   without a full re-extract.

### 8. Tests

A new table is a
config-entry change and does **not** warrant a unit test — asserting that a config
value equals a retyped copy of itself catches no bug. The verification in step 7 and
the DQA reconciliation are what cover it.

Write a test when the table forced you to add *logic*: a custom `select_from_expr`
whose SQL you want pinned, a non-obvious delta expression, or a pre-merge hook.

### New-table checklist

- [ ] Grain, primary key, delta column, delete semantics and volume investigated and written down
- [ ] `CREATE TABLE` added to the archive DDL (plus a migration if an existing table changed)
- [ ] `DfmExtractConfig` added, `checkpoint_from` pointing at the **arc** table
- [ ] Oracle only: `columns`, `column_types`, `index_keys` set
- [ ] `ArchiveMergeConfig` added; `merge_keys` + `non_key_columns` cover every column
- [ ] `checkpoint_query` uses `CONVERT(..., 121)`, or is omitted for full load
- [ ] Delete behaviour chosen deliberately
- [ ] The code location loads and the assets appear in the Dagster UI after the push
- [ ] First run loads, second run is a no-op, grain check passes, replay leaves the checkpoint alone
- [ ] DQA subject added

## Common pitfalls

| Symptom | Cause |
|---|---|
| Run fails at the end with a checkpoint validation error | `checkpoint_query` used `CAST` instead of `CONVERT(..., 121)` |
| Every run re-merges the whole table | Delta column does not update on change, or `checkpoint_from` points at `ext` instead of `arc` |
| Downstream counts are inflated | `merge_keys` is not the real grain — verify with the `COUNT(DISTINCT ...)` check |
| A column is always NULL in `arc` | It is missing from `non_key_columns` |
| `TypeError: merge_keys must be a tuple` | Missing trailing comma in a one-element tuple |
| Delete detection "does nothing" | Silently disabled on a delta run — see the warning in the logs |
| Oracle archive MERGE is extremely slow | `column_types` missing, so key columns landed as `NVARCHAR(MAX)` and cannot be indexed |
| IDs do not match downstream after an Oracle extract | Numeric ID stringified as `"123.0"` — `stringify_oracle_value()` handles this; check the column is in `column_types` |
| Asset does not appear in Dagster | Not exported through the `__init__.py` chain, or the config was never appended to the list |
